
## 形

**本のフォルダが状態そのもの。** 1 冊 1 フォルダ (`~/Downloads/kindle/<ASIN>/`)。各段は自分の成果物だけを書き、書いた段の版を入れる。本の状態は「成果物がない・古い・今の版で落ちた最初の段」で、`books.progress.json` は持たない (model-the-domain、derive instead of sync)。段は表 1 つ (`kc/book.py` の `STAGES`): `capture → ocr → layout → assemble → verify → publish`。書くのは `*.tmp` に書いてから rename なので、途中で落ちても半端なものは残らない (make-operations-idempotent)。

**段の版は入力から出す。手で上げない。** `ocr` の版は OCR のコードのハッシュ、`layout` の版はプロンプトとスキーマとモデル名のハッシュ。コメントを直しただけで Gemini の枠を使って全冊を読み直すことはない。変換を直せば、前に落ちた本も通った本も、版が変わった段から自動でやり直す (`converter_version`・`stale_failure`・`stale_pass` を置き換える)。

**落ちた本だけ止める。** 失敗は 2 種類。`BookFault` はその本を `Parked` にして次の本へ進む。`SystemFault` (ログインが切れた、Gemini の枠切れ、拡張に届かない、同じチェックが 2 冊続けて落ちた) は、その段の列だけを止めて時刻か新しいコードで自動で再開する。ログイン切れだけは Laiken に macOS の通知を出す。`Parked` の本は、落ちた段の版が変わると自動でもう一度走る。人の「再開して」は要らない (STOP_CHECKS と終了コード 2 の約束を消す)。

**拡張と Python の間に通信路を 1 本。** `kc run` が `127.0.0.1` に小さな HTTP の口を開く。拡張の worker はそこから仕事 (ASIN、ドメイン、取り直しか) を受け取り、自分でタブを開き、ページを 1 枚ずつ送り、終わったらタブを閉じる。Python は受けたページをすぐ `pages/NNNN.png` に書く。止まっても次はそこから続く。これで消えるもの: URL の印、ダウンロードフォルダの見張り、ZIP、タブ名の心拍と osascript、閲覧履歴と Preferences の読み取り、保存ダイアログの設定、タブを閉じる osascript、タブを 2 つ開かない仕組みの大半。1 冊を取り込むのは 1 つの仕事だけなので、重複は口の側で 1 か所で止まる。

**拡張は自分で再読み込みする。** 口は「ディスクの拡張の版」を返す。worker は仕事がないときに自分の版と比べ、違えば `chrome.runtime.reload()` を呼ぶ (読み込み元はこの checkout なので、pull した新しい版が読まれる)。Laiken のリロードは要らない。**未確認**: 最初の 1 回 (この仕組みを入れる版) だけは手で読み込む必要がある。

**Mac は自分で main を取る。** `kc run` は 1 歩ごとに `git pull --ff-only` をして 1 つの仕事をして戻る。Python が変われば launchd が新しいコードで起こし直す。`os.execv`・`update_checkout`・「pull main と打って」は消える。checkout に書きかけがあって pull できなければ `SystemFault` (理由つき) で止まる。

**ページめくりの判断は 1 つの純関数。** `extension/policy.js` の `nextAction(state, observation)` が、先頭へ戻る・めくる向き・最後の判定・止まりの判定を全部決める。拡張は観察 (足元の位置、画像のハッシュ、画面の種類) を作って関数に渡し、返った動作をするだけ。観察と動作は全部 `trace.jsonl` に残る。クラウドは同じ関数に trace を流し直して、Mac で起きたことを Node のテストで再現する (C3 から)。めくる向きは「押して位置の数が増えたほう」で決めるので、縦書きの本に言語ごとの分岐は要らない。

**失敗はクラウドで再生できる記録になる。** 失敗するたびに `cases/<id>/` (失敗したチェック、trace、画面の構造、関係するページ画像 2〜3 枚) を書き、Drive の `Kindle_cases/` に写す。クラウドの定時の仕事 (routine) が 1 時間ごとに Drive を読み、新しい記録ごとに台帳に 1 行足し、再生テストを作って直す。手で書いた画面の木と `expect.json` はこれに置き換わる。

**本文は OCR、構造は LLM、という今の分担は残す。** 実験のとおり LLM は書き起こしを断るので、本文は Mac の Vision。LLM は本文を返さず行番号で構造だけを答える (今の `layout.py`)。縦書きの日本語は Vision では読めないので、縦書きを読める OCR を X5 の結果で選ぶ。

**Drive に書くのは検査を通った本だけ。** 今の `publish()` は失敗でも Drive に写す (`capture_book.py:341`、ルール表と食い違い)。`publish` は `Verified` だけを受け取り、`Verified` を作れるのは `verify` だけにする (encode-lessons-in-structure)。

## 決めたこと (arena)

3 案を別々に設計させ (opus 2、sonnet 1)、別のモデルに採点させた。3 案とも「ブラウザを自分で持つ、状態はファイルから出す、落ちた本だけ止める、Mac は自分で main を取る、失敗はクラウドで再生できる記録にする、本文は LLM」に収束した。採点は案 1 (25 点) > 案 2 (23) > 案 3 (22) で、私の読みも案 1 を土台にした。理由は、失敗の記録の戻り道が今ある Drive で具体的なこと、検査が目次と見出しの照合まであること、未確認の前提の並べ方が一番正直なこと。

案 1 から取ったもの: 状態をファイルから出す `STAGES` の表、失敗の 2 種類と自動再開、段の版で自動やり直し、型で Drive への書き込みを止める、Drive に失敗の記録を置く。
案 2 から: ページを 1 枚ずつ保存して途中から続ける。見本のページのテキスト層を正解として OCR の正しさを測る (下の「未確定」)。
案 3 から: めくりの判断を純関数 1 つにし、trace を残してクラウドで再生する。めくる向きを位置の増減で決める。

実験で捨てたもの: 3 案共通の「LLM が本文を書く」(Claude が断った) と「自分専用の Chrome」(Mac の自動許可が止めた)。代わりに、今ある拡張に通信路と自動再読み込みを足す。これは 3 案とも「ブラウザを自分で持てなかったときの代わり」に挙げていた形。

## 引き受けたもの

- Laiken の Chrome を共有し続ける。代わりに、2 回目のログインも、Amazon に別のブラウザと見なされる危険もない。
- OCR の読み違いを直す仕組み (`proofread.py` の検出) は残る。LLM が書き起こさない以上、本文の正しさは OCR と検査で守るしかない。新しく足すのは本ごとの例外ではなく、見本のテキスト層で測れるものに限る。
- 拡張を入れ替える最初の 1 回は、Laiken の手でのリロードが要る (以後は自動、の見込み)。
- 失敗の記録に Drive を使う。Mac から GitHub に書く資格は持たせない。

## 捨てた案

- **自分専用の Chrome を CDP で動かす。** 拡張・リロード・横道を全部消せる、一番きれいな形。Mac の自動許可が止めたので、Laiken が許可とログインを 1 回するなら戻せる。そのときは通信路の口を CDP に替えるだけで、ほかの形は変わらない。
- **LLM に本文を書き起こさせる。** OCR の修正の層を全部消せるが、Claude は断った。
- **今の形のまま直し続ける。** 3 つの層に散った見張りと横道が残り、1 件ずつの往復も残る。
